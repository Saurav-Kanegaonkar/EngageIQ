EngageIQ, how the data is stored and flows

Two SQLite databases, kept separate on purpose: engageiq.sqlite, read-only corpus engage.sqlite, read-write user state

Everything in the user database is scoped to (user_id, persona_key): one browser is one user, each persona is one key. The corpus is referenced by opportunity_id across the two files.

Lifecycle: pick a persona → /api/recommend saves it + reads its weights → you react → /api/feedback updates interactions, logs an event, trains the learner → /api/activity reads it all back → the next recommend re-ranks with the new weights.

3The feedback loop (why the feed reorders when you return)

Each reaction nudges a weight vector. The very next time the feed is built, those weights are loaded, so liked-style items rise and disliked-style items sink. On return it is automatic, no button needed.

flowchart LR
  U(["You react:
engage / dismiss / save"])
  FE["POST /api/feedback"]
  LS[("learner_state:
your weight vector")]
  IN[("interactions:
each card's state")]
  RE["POST /api/recommend
(reload or next visit)"]
  FEED(["Re-ranked feed:
liked-style items rise,
disliked-style sink"])
  U --> FE
  FE -->|"reward: engage 1.0 / save 0.8 / dismiss 0.0"| LS
  FE -->|"status + reason"| IN
  LS -->|"loads your learned weights"| RE
  IN -->|"restores card states"| RE
  RE --> FEED
  FEED -.->|"you keep reacting"| U

The weights persist per (user, persona), so the loop survives a refresh and a return visit. Within one sitting the on-screen feed holds still while you read; it re-sorts when you reload, re-enter the hub, or tap "Re-rank with my feedback".
